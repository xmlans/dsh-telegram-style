# D47. 构建产物随主分支提交

## 背景

插件市场对还没收录、或收录条目里没有 npm 包名的插件，按 `github:作者/仓库` 安装，拿到的是默认分支的内容，不读发布分支，也不执行构建。主分支没有构建产物时，宿主找不到 `lib/host/index.js`，安装被回滚。

## 决定

- 主分支提交 `lib/`：改了源码就运行 `npm run build`，把 `lib/` 和源码放进同一次提交。源映射（`*.map`、`*.map.br`）不提交，与 npm 包一致。
- `lib/` 在 `.gitattributes` 里标为生成文件、不显示差异；持续集成的范围判断不把 `lib/` 的改动算作代码改动。
- 发版仍由持续集成完成：构建一次，上架的内容与通过验证的那份产物是同一份；同一次发版把相同的文件写到只由持续集成写入的发布分支，并把版本标签移到那次提交上。
- 发布前核对标签与包声明的版本一致，不一致即失败；先发预发布版本，全部闸门通过之后再发正式版本并设为默认标签；上架走一次性凭据与来源证明，仓库不保存发布令牌。

## 后果

- 从主分支的任意提交都能直接安装，不必构建。
- 每次改源码都要多一步构建并提交 `lib/`；忘了构建时，主分支上的产物会落后于源码，从 GitHub 安装的人拿到旧版本。
- 提交里多出构建产物的改动，在 GitHub 的改动视图里默认折叠。

## 重审条件

- 宿主能在安装代码仓库里的插件时自动执行构建，或插件市场只从包管理器安装时，主分支不再提交 `lib/`。
